# ADR-010: Worktree enforcement semantics — what G-Forge governance should mean in a `git worktree`

**Date:** 2026-07-02
**Status:** Proposed (awaiting developer ratification)
**Reversibility:** two-way door (reversible) — this ADR selects a semantic stance and, if B or a hybrid is chosen, a propagation seam; the seam is additive (new hook logic / new sentinel scoping), not a rewrite of the existing hook or sentinel contracts. Reversing means turning the seam back off; it does not require unwinding committed data.
**Context:** Audit finding 10 (Major, High change-risk), `g-docs/milestones/M-audit-2026-07.md` item 10 — "Worktrees have no `.claude/` (gitignored) → all seven hooks silently off in `isolation: worktree` agent sessions." This ADR is the design spike; no implementation code changes with it.

## Context

G-Forge's enforcement model depends entirely on a project's committed `.claude/` firing hooks on every client (ADR-003 names this "enforcement that travels" as the project's spine). Concretely, `.claude/settings.json` registers seven hooks (`UserPromptSubmit` → `workflow-checkpoint.sh`, `PreToolUse`/`PostToolUse` on `Bash|PowerShell` → `check-commit.sh` / `post-commit-cleanup.sh` / `observe.sh`, `SubagentStart`/`SubagentStop` → `agent-lifecycle.sh`, `PreCompact` → `pre-compact.sh`, `SessionStart` → `session-start.sh` + `observe.sh session`). Every one of them is invoked via `$(git rev-parse --git-common-dir)/../.claude/hooks/<script>.sh` — a path built off `git-common-dir`, which resolves to the **main repository's** `.git` from any worktree, not the worktree's own.

Two facts were verified directly against this repo, not assumed:

1. **`.gitignore` line 5** ignores `.claude/` (and `.worktrees/`) wholesale at the top level. `git check-ignore -v` confirms `.claude/settings.json`, `.claude/hooks/check-commit.sh`, and `.claude/g-forge-approved` are all matched by that one line — nothing under `.claude/` is committed. (`g-docs/`, by contrast, *is* committed — tracking already lives outside `.claude/` per the `.gitignore` header comment.)
2. **A live scratch worktree was created and inspected in this session.** `git worktree add` against this repo's `HEAD` produces a working tree with **no `.claude/` directory at all** — confirming audit finding 10 literally, not hypothetically. From inside that worktree, `git rev-parse --git-common-dir` correctly resolves to the **main repo's** `D:/SW_Projects/G-Team/.git` (while `--git-dir` resolves to the worktree-local `.git/worktrees/<name>`) — so the `git-common-dir` trick in `.claude/settings.json`'s hook commands, if invoked, *would* correctly reach the main repo's hook scripts.

The actual failure mechanism is one layer deeper than "no hooks directory," and it is decisive: **every one of the seven hook scripts self-guards with a relative-path check, `[ -f ".claude/integration-tier" ] || exit 0`, evaluated against the invoking process's current working directory** (confirmed via grep across `check-commit.sh`, `post-commit-cleanup.sh`, `observe.sh`, `agent-lifecycle.sh`, `pre-compact.sh`, `session-start.sh`, `workflow-checkpoint.sh`). In a worktree session, cwd is the worktree root, which has no `.claude/integration-tier` (gitignored, never checked out there). So even in the hypothetical where Claude Code *did* discover and invoke `.claude/settings.json`'s hook commands from a worktree session, **every hook would see its own guard fail and exit 0 silently** — no commit gate, no observer journal, no checkpoint banner, no agent-lifecycle logging, no compaction snapshot, no session-start sync. This is a second, independent fail-open path layered on top of the more basic question of whether a worktree session even discovers `.claude/settings.json` in the first place (it has no local copy to discover; Claude Code's settings-resolution behavior for worktree cwds was not verified live in this spike and is called out as an open question below).

**ADR-003 precedent, and why it does not simply transfer:** ADR-003 ruled Claude Cowork "not a G-Forge host" because hooks structurally never fire there — an architectural gap in the client, permanent until Anthropic changes it, with an explicit re-probe trigger. A worktree is different in kind: it is not a separate client, it is a second working tree of *the same repository*, on *the same machine*, under *the same Claude Code binary* that fires hooks correctly in the main tree. The gap here is self-inflicted by G-Forge's own convention (`.claude/` is gitignored) colliding with how `git worktree` populates a new tree (from the committed index only) — not a host that structurally cannot fire hooks. That means, unlike Cowork, this is fixable by G-Forge's own hand, which is exactly why this ADR must pick a stance rather than defer to "wait for the vendor."

## Options considered

**A. Worktrees are enforcement-exempt by design.** Treat every worktree as an agent-only sandbox: single-use dispatched agents never commit (HQ-only commits is a G-RULES §B hard stop — "Never instruct subagents to commit — they implement and return results only"), so if the convention holds, no worktree session ever reaches `git commit`, and an absent gate there is moot. Simplest option, and it matches the Agent tool's own framing of `isolation: "worktree"` as an agent-execution isolation mechanism, not a human workspace.

**B. Enforcement must travel to worktrees.** Populate the worktree's `.claude/` (or make the hooks worktree-aware) so all seven hooks fire identically to the main tree. Two sub-mechanisms are plausible: (b1) a `SessionStart`-equivalent step that copies/symlinks `.claude/hooks/`, `.claude/settings.json`, and `.claude/integration-tier` into the new worktree before the agent's first turn; or (b2) rewrite the hooks' self-guard to resolve `.claude/integration-tier` via `git rev-parse --git-common-dir` (the same trick `settings.json` already uses for the hook path itself) instead of a bare relative path, so the guard — and everything downstream that reads sentinel/state files by relative path — becomes worktree-transparent without copying anything.

**C. Detect-and-warn.** Leave hooks off in worktrees (accept the fail-open), but make the *absence* visible instead of silent: the main session's `workflow-checkpoint.sh` reports "N worktrees active, unenforced," and `/g-doctor` gets a check that flags any registered worktree lacking a populated `.claude/`. Converts silent fail-open into visible fail-open. Does not, by itself, close the human-commits-in-a-worktree gap named as A's risk — it only surfaces it.

**D. Hybrid — split by occupant, not by mechanism.** Apply **A's reasoning to agent-dispatched worktrees** (the Agent tool's `isolation: "worktree"` sessions: single-use, never commit, HQ integrates and commits afterward, so an unenforced gate there is inert by G-RULES' own commit ownership rule) **and C's reasoning to human-occupied worktrees** (a developer who runs `git worktree add` by hand and might commit directly from it, where a silent fail-open is a real gap, not a moot one). Detection distinguishes the two by *who is committing*, not by wiring B's full hook-propagation machinery everywhere.

## Decision

**Adopt Option D — split enforcement semantics by worktree occupant, not by uniform propagation.**

- **Agent-dispatched worktrees** (`isolation: "worktree"` from the Agent tool) are **enforcement-exempt by design (Option A's reasoning applies as-is)**. The single-use agent contract already forbids these sessions from running `git commit` — commits are HQ-only, done after the agent's result is integrated into the main tree (G-RULES §B, §C). An unenforced gate in a working tree that structurally never reaches `git commit` is not a gap; it is inert by construction, the same way a read-only reviewer agent's missing Write tool is not a "gap." No hook propagation is needed for this occupant class, and building it (Option B) would add machinery to close a door nothing walks through.

- **Human-occupied worktrees** (a developer running `git worktree add` directly, outside agent dispatch) get **Option C, detect-and-warn** — not B. `workflow-checkpoint.sh`'s existing per-prompt output gains a line surfacing any registered worktree (`git worktree list`, parsed from the main session, which always has a correctly-populated `.claude/`) whose path lacks a `.claude/integration-tier` file, and `/g-doctor` gets a corresponding check. This makes the fail-open **visible instead of silent** without attempting to make hooks fire identically in a tree that was never designed to carry `.claude/` state.

**Why not B outright (full hook propagation to every worktree):** rejected primarily on the sentinel-scoping question, which this ADR must answer explicitly rather than leave implicit — **is `.claude/g-forge-approved` (and every other stateful sentinel: `tier3-active`, `review-holds`, `session-compaction-count`, `roundtable`) per-worktree or per-repo?** These sentinels currently live at a single relative path with no repo/worktree identity encoded in them. If B copies or symlinks `.claude/` into each worktree, the *simplest* implementation shares the sentinel files (symlink or shared absolute path), which reintroduces exactly the cross-talk failure named as B's risk in the dispatch brief: a `MERGE READY` approval earned in worktree X writes `.claude/g-forge-approved`, and if that file is shared or path-resolved back to the main repo's copy, worktree Y's commit gate opens on an approval it never earned — **worse than no gate, because it looks enforced while being wrong.** A *correct* B implementation would need each sentinel to be either physically per-worktree (duplicated state, now needing its own sync/eviction story) or content-bound to the specific diff it approved (the mechanism designs 008/009 are drafting in parallel this wave, per the dispatch brief). Until content-bound, time-evicted sentinels exist, B cannot be built safely — it would be layering a propagation fix on top of a sentinel model not yet designed to be shared across trees. This ADR does not duplicate 008/009's content; it records the dependency: **if 008/009 land a content-bound sentinel design, B becomes buildable for the human-occupied case without the cross-talk risk, and this decision should be revisited then** (see Consequences).

**Sentinel-scoping answer for this decision (D, not B):** moot for the agent-exempt case (no sentinel is ever written or read there, since no hook fires and no commit happens). For the human-occupied detect-and-warn case, no sentinel propagation is introduced at all — `/g-doctor` and `workflow-checkpoint.sh` read worktree *presence/absence* of `.claude/integration-tier`, not sentinel *content*, so there is nothing to scope per-worktree yet. This sidesteps the scoping question rather than resolving it — the question stays open and explicitly deferred to a future B reconsideration gated on 008/009.

## Consequences

- **Easier:** the recurring "why don't hooks fire in a worktree?" question is answered with a mechanism trail (gitignore → no `.claude/` → relative-path guard fails → all seven hooks exit 0), not a guess. Agent-dispatched worktrees need zero new code — the exemption is already true by virtue of the existing commit-ownership rule, so this ADR mostly *ratifies* current behavior for that occupant class rather than changing it. Human-occupied worktrees get a cheap, low-risk visibility fix (`workflow-checkpoint.sh` + `/g-doctor` additions) with no sentinel-sharing risk.
- **Harder / constrained:** a human developer who deliberately works from a worktree (not uncommon for parallel-branch work) still gets no commit gate *enforcement* there — only a warning that they are unenforced. They can still commit non-conforming work from a worktree today, and D does not close that; it only makes the gap visible. If that residual risk is judged unacceptable by the developer, the next step is B gated on 008/009, not a re-litigation of D.
- **Follow-up decisions:** (1) whether Claude Code's own settings-resolution even discovers `.claude/settings.json` in a worktree session at all was not verified live in this spike (the git-common-dir path-construction *inside* the hook commands was verified; whether those commands are ever reached from a worktree cwd was not) — flagged as an open verification item, not resolved here. (2) Revisit B for the human-occupied case once 008/009's content-bound, time-evicted sentinel design lands — re-run this ADR's sentinel-scoping analysis against that design specifically. (3) `/g-doctor`'s new worktree check and `workflow-checkpoint.sh`'s new warning line are unspecced implementation details deferred to a future `/g-plan` pass; this ADR fixes the semantics, not the code.
- **Unaffected:** the main working tree's enforcement is untouched by this decision; nothing here weakens any existing hook, sentinel, or gate in the primary repo.

## Constraints that drove this decision

- G-RULES §B's hard stop — "`git commit` is HQ-only… Never instruct subagents to commit" — is what makes Option A's exemption *true by construction* for agent-dispatched worktrees, not just a convenient assumption.
- `.gitignore`'s top-level `.claude/` ignore (verified line 5) is a deliberate, pre-existing convention (runtime artifacts vs. committed tracking in `g-docs/`) that this ADR does not propose changing — reversing that convention was out of scope for this spike and would be a separate, larger decision.
- Sentinel files (`g-forge-approved` and siblings) currently carry no repo/worktree identity, which is the concrete reason B is unsafe today — this is a hard blocker on B, not a style preference.
- ADR-003's precedent shape (host-capability gap → explicit ADR + re-probe trigger, not silent workaround) is followed here, adapted: this gap is self-inflicted and fixable, so the "trigger" for revisiting is a design dependency (008/009 landing) rather than an external vendor decision.

## Assumptions that held (with fragility)

- **Worktrees have no `.claude/` at all** — *confirmed live* via a real `git worktree add` against this repo's `HEAD` and directory inspection, not inferred from `.gitignore` alone.
- **`git rev-parse --git-common-dir` resolves to the main repo's `.git` from inside a worktree** — *confirmed live*, so the hook-path construction in `.claude/settings.json` is not itself the broken part.
- **All seven hooks share the identical relative-path self-guard** — *confirmed via grep* across all seven hook scripts; this is the actual, uniform failure mechanism, not a per-script inconsistency.
- **Agent-dispatched worktree sessions never call `git commit`** — *holds by G-RULES §B's explicit rule*, but is enforced by convention/agent-prompt discipline, not by a technical barrier inside the worktree itself. *Fragile*: if that rule were ever violated (a misbehaving or off-spec agent issuing a commit anyway), Option A provides no backstop — there is no hook there to catch it. This fragility is accepted for D because the same G-RULES contract already governs every other aspect of agent behavior (scope, file boundaries, single-attempt discipline) without a technical enforcement backstop, and is judged consistent with that existing trust model — but it is named here explicitly rather than assumed away.

## Premortem — top 3 ways Option D fails

1. **An agent-dispatched worktree commits anyway** (bug, prompt injection, or a future agent type that doesn't honor the HQ-only-commits rule) and, because Option D deliberately installs no gate there, the non-conforming commit lands with zero enforcement and zero warning — silent by design, not just silent by omission. Mitigation would require either a lightweight universal guard (contradicts D's "no propagation for agent worktrees" premise) or stronger agent-prompt/tooling-level enforcement outside this ADR's scope.
2. **The human-occupied detect-and-warn signal is too easy to ignore.** A warning line in `workflow-checkpoint.sh` output competes with everything else already printed there (branch, milestone, review state, Tier 3 status); if a developer's eyes skip it, the practical effect is identical to Option A's silent exemption, just with an unread line added. This risks becoming warning-fatigue theater rather than real risk reduction unless `/g-doctor` (a deliberately-run check, not passive output) carries the real teeth.
3. **008/009 land a sentinel design that makes B safe, and D quietly becomes permanent because nobody re-opens this ADR.** The explicit follow-up ("revisit B once content-bound sentinels exist") depends on someone remembering to trigger that revisit — there is no automatic re-probe mechanism here analogous to ADR-003's named external trigger conditions. Without a concrete owner or hook for the re-check, D's "for now" framing risks calcifying into "forever" by default.
