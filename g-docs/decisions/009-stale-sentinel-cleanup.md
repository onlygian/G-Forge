# ADR-009: Stale-sentinel cleanup-on-check (terminal-commit staleness)

**Date:** 2026-07-02
**Status:** Proposed
**Reversibility:** two-way door — the eviction rule lives entirely inside `check-commit.sh` (and optionally `post-commit-cleanup.sh`); removing it restores current (permissive) behavior with a one-line revert.
**Context:** Audit finding 9 (Major, `g-docs/milestones/M-audit-2026-07.md`) — `hooks/post-commit-cleanup.sh` only deletes `.claude/g-forge-approved` / `.claude/g-forge-docs-approved` when the commit runs through a matched Claude Code tool event (`Bash`/`PowerShell` `PostToolUse`). A commit made in a plain terminal outside Claude Code never fires that hook, so the sentinel written by an earlier `/g-review` survives past the commit it was meant to gate — and the **next** in-session commit rides that stale approval without a fresh review.

## Design

**Mechanism: cleanup-on-check.** Move the staleness check into `check-commit.sh` (the gate itself), not `post-commit-cleanup.sh` (the cleanup hook). Rationale: `post-commit-cleanup.sh` only runs as a reaction to a Claude-Code-mediated `git commit` — by construction it can never observe a terminal commit, since that event never invokes any Claude Code hook at all. Only the *next* gated commit attempt (which always fires `check-commit.sh`, a `PreToolUse` hook on `Bash`/`PowerShell`) has an opportunity to notice that the sentinel predates HEAD. `post-commit-cleanup.sh` keeps its existing unconditional-delete behavior (§Consumer updates) as a fast-path for the common in-session case; the new eviction rule in `check-commit.sh` is the backstop that closes the terminal-commit gap.

**Eviction rule (informal):** at gate time, if a required sentinel exists AND its authoritative timestamp is older than (strictly earlier than) HEAD's commit timestamp, treat the sentinel as consumed by that earlier commit — delete it and deny the current commit attempt with a message directing the developer to re-run the appropriate review skill.

**Authoritative timestamp source — decision and precedence:**

1. **Preferred: content timestamp (per ADR-008).** If ADR-008 (sentinel content-binding) has shipped, the sentinel file contains a timestamp line (e.g. `approved-at: <unix-epoch>` or equivalent field written by `/g-review` Step 6 / `/g-doc-review`). When that field is present and parses as an integer, it is authoritative — it reflects when the review verdict was actually issued, independent of filesystem mtime, which is fragile across `git clone`, `git checkout`, worktree creation, and any tool that touches the file without changing its meaning (e.g. antivirus scans, backup tools, `touch`).
2. **Fallback: file mtime.** If the sentinel has no parseable content timestamp (legacy sentinel written before ADR-008 lands, or ADR-008 is not yet implemented), fall back to the file's modification time via a portable method (see §Windows note). This is strictly a compatibility fallback — mtime is known-fragile, but a missing timestamp must not disable the eviction rule entirely, since that would silently reintroduce the exact bug this ADR fixes.
3. **HEAD commit time** is always read via `git log -1 --format=%ct` (committer-date Unix epoch, seconds). This is git-native, portable, and unambiguous across platforms — no shell `stat` involved.

**Standalone requirement:** this design does not depend on ADR-008 shipping. If ADR-008 never lands, step 2 (mtime fallback) is the sole comparison path and the rule still functions — degraded (fragile across checkout/clone) but still closes the terminal-commit gap for the common same-machine, same-checkout case that this finding is about. If ADR-008 ships first or later, its content timestamp transparently promotes the fallback into the preferred path with no further code change beyond parsing the new field.

**Interaction with ADR-008 (content-binding):** ADR-008 binds a sentinel to a specific reviewed tree (diff hash). That check answers "does the sentinel match the tree being committed right now?" This ADR (009) answers a different question: "does the sentinel predate a commit that already consumed it?" The two are complementary, not redundant, and can both fire on the same gate invocation:
- If **both** mechanisms are present: run the ADR-008 content/hash check first (it is the stricter, more precise check — a hash mismatch is unambiguous evidence of a stale review regardless of timing). If ADR-008 already denies (hash mismatch), stop there — do not additionally evaluate timestamp staleness; report the hash-mismatch reason.
- If ADR-008's hash check **passes** (tree matches), still run this ADR's timestamp check. A matching hash does not on its own prove the sentinel is post-HEAD — a pathological case (rebase reordering, cherry-pick reproducing an identical tree) could match hashes while genuinely being older than the current HEAD. Timestamp staleness is the belt to content-binding's suspenders.
- **Which check wins on conflict:** ADR-008 (content mismatch) wins as the higher-precision signal when both would deny for different reasons — but in practice they should agree in the overwhelming majority of cases (a stale sentinel is usually both hash-mismatched and time-stale). Only report one reason to the developer per gate run: content-mismatch reason takes precedence in the message when both would fire.
- If ADR-008 has **not** shipped: this ADR is the sole enforcement mechanism and runs unconditionally per §Where the check runs.

## Timestamp comparison

**Comparison operator:** the sentinel is stale **iff** `sentinel_timestamp < head_commit_timestamp` (strict less-than). Equality (same-second sentinel write and commit) is treated as **not stale** — the sentinel is honored. Rationale for the tie-break direction: `/g-review` always writes the sentinel *before* the commit it approves is made (Step 6 happens pre-commit, by construction — the whole point of the gate is review-then-commit), so a sentinel timestamped in the same second as HEAD is virtually always "written for this exact commit," not "written after." Defaulting the tie to "not stale" avoids spuriously evicting a just-issued approval on fast CI machines or scripted test harnesses where write-then-commit can land in the same wall-clock second. This is the one place this design intentionally does **not** default fail-closed, because failing closed here would make the gate flaky (intermittently deny a legitimate same-second approve-then-commit sequence) rather than safer — the actual risk (a stale sentinel surviving) is bounded by "at most one extra second of staleness," which is not a meaningful attack surface.

**Clock skew:** if the sentinel's authoritative timestamp is *ahead* of HEAD's commit time (sentinel appears to be from the future relative to HEAD), treat this as **not stale** (the comparison `sentinel_timestamp < head_commit_timestamp` is already false in this case, so no special-case code is needed) but do not attempt to "correct" or warn about clock skew — this design does not add clock-skew detection/warning logic; it is out of scope. A sentinel timestamped after HEAD is the expected, common case (review happens, then commit happens) and requires no special handling.

**Formal rule:**
```
sentinel_ts = parse_content_timestamp(sentinel_file)   # ADR-008 field, if present and valid
if sentinel_ts is empty or unparseable:
    sentinel_ts = mtime(sentinel_file)                  # portable fallback, see Windows note
head_ts = $(git log -1 --format=%ct 2>/dev/null)

if head_ts is empty (no HEAD — see Edge cases "first commit"):
    skip eviction check entirely — do not evict, do not deny on this basis
elif sentinel_ts < head_ts:
    stale → delete sentinel, deny with:
        "approval consumed by an earlier commit — re-run /g-review"
        (or "re-run /g-doc-review" for the doc sentinel — see Consumer updates)
else:
    sentinel is current → proceed with existing gate logic (sentinel presence/absence check unchanged)
```

## Edge cases

| Case | Expected behavior | Fail open/closed | Rationale |
|------|-------------------|-------------------|-----------|
| **Amend** (`git commit --amend`) | HEAD's commit time updates to the amend time even if the tree is identical. If the sentinel predates the amend, it is evicted (same as any other stale case) — the developer must re-run review even though content may be unchanged. | Fail-closed (evict, deny) | An amend is still "a commit happened since the sentinel was written" from the gate's point of view; the gate cannot cheaply prove the amended tree is identical to what was reviewed (that provability is ADR-008's job, not this one). Re-review is the safe default. |
| **Rebase** (interactive or otherwise) | All rewritten commits get new commit times (at minimum, the rebase completion time is ≥ the original author time for replayed commits, and `%ct` reflects committer time which rebase updates). Any sentinel written before the rebase is evicted on the next gate check. | Fail-closed (evict, deny) | Rebase is exactly the class of history-rewrite this rule exists to catch — a sentinel approved against pre-rebase HEAD must not silently authorize a post-rebase commit. |
| **First commit in repo** (no HEAD exists yet — `git log -1` fails/empty) | Skip the eviction check entirely. Fall through to existing sentinel presence/absence logic (unchanged) — i.e. the gate behaves exactly as it does today when there is no timestamp to compare against. | Fail-open **for the eviction check only** — but the underlying sentinel-presence gate (existing behavior) still applies and is unaffected. | There is no "earlier commit" to have consumed the sentinel — the staleness question is undefined, not false. Attempting to force a comparison against a missing HEAD would either crash the hook or require an arbitrary sentinel value; skip is the only correct behavior. This does not weaken enforcement: a first commit with no sentinel still gets denied by the existing presence check. |
| **Sentinel written, then NO commit yet** (developer ran `/g-review`, got MERGE READY, sentinel exists, HEAD is still the pre-review commit) | Must NOT evict. `sentinel_ts` (written just now) is >= `head_ts` (the older, already-existing HEAD) in the overwhelming common case, so the `sentinel_ts < head_ts` comparison is false and the sentinel is correctly treated as current. | N/A — this is the base case the comparison must preserve, not evict | This is the primary intended-use path (review → sentinel → commit) and must be unaffected. Getting the comparison direction wrong here (evicting a fresh, unused sentinel) would break every normal `/g-review` → commit flow, so this case is the canonical correctness check for the rule. |
| **Multiple quick commits in one turn** (commit A lands, sentinel survives because same review covers a follow-up commit B in the same session — e.g. a fixup) | If the sentinel predates commit A (HEAD after A), the next gate check (for commit B) evicts it — commit B is denied and must go through review again, UNLESS `post-commit-cleanup.sh` already deleted it after commit A (the common in-session path, unaffected by this ADR). This ADR's eviction only matters when `post-commit-cleanup.sh` did NOT run (terminal commit A, then an in-session commit B attempted next) — in that scenario, eviction at the `check-commit.sh` gate for commit B is exactly the fix this finding calls for. | Fail-closed (evict, deny) | Two commits under one sentinel is precisely the bug being fixed — one review must not silently cover more than the one commit it was written for. |
| **Detached HEAD** | `git log -1 --format=%ct` still resolves normally in detached HEAD (it reads the current HEAD ref regardless of branch attachment) — behavior is unchanged from the normal-branch case. | Same as normal case (fail-closed on staleness) | Detached HEAD does not change what "HEAD's commit time" means; no special-case logic is needed. |
| **Both sentinels present, different ages** (e.g. code sentinel is current, doc sentinel is stale — or vice versa) | Evaluate each sentinel's staleness **independently** against the same `head_ts`. A stale sentinel is evicted and denies the commit on its own basis even if the other sentinel (for the same commit) is still current. A `mixed`-class commit (per `check-commit.sh`'s existing classifier) needs both sentinels current; if either is stale, deny citing that specific sentinel. | Fail-closed (evict whichever is stale, deny) | The two sentinels gate two independent review surfaces (code vs. docs per the two-gate model, `g-rules-G-documentation.md`); staleness of one must not be masked by freshness of the other, and vice versa. |

**Default posture:** every edge case above defaults **fail-closed** (evict + deny + require re-review) except the two cases where "fail-closed" is not a meaningful concept (first commit — no comparison possible; and the base "just reviewed, not yet committed" case, which is not actually an eviction scenario at all). This matches the constraint stated in the task: default fail-closed.

## Windows note

All of this logic runs under Git Bash on Windows (per the hook shebang `#!/bin/bash` and the project's hook execution model). `stat` is **not** portable across the platforms G-Forge hooks must run on — GNU `stat` (Linux, Git Bash's coreutils) uses `stat -c %Y file`, BSD/macOS `stat` uses `stat -f %m file`, and neither flag set is accepted by the other. Do not write a `stat`-based mtime check without a platform branch.

Preferred approaches, in order:
1. **Avoid `stat` entirely where possible** — the content-timestamp path (ADR-008 field) requires no filesystem timestamp at all, just a `grep`/parse of the sentinel's contents. This is the portable, preferred path and is one more reason to treat content-timestamp as authoritative over mtime.
2. **When mtime fallback is unavoidable** (legacy sentinel, ADR-008 not shipped): use a portable method that does not fork platform-specific `stat` flags. Options, in preference order:
   - `git log -1 --format=%ct -- <sentinel_path>` — **does not work**, since `.claude/g-forge-approved` and `.claude/g-forge-docs-approved` are gitignored/untracked sentinel files, not committed content; git has no history for them. Ruled out.
   - A `find`-based portable mtime: `find "<sentinel_path>" -printf '%T@\n'` — GNU-only (`-printf` is a GNU extension), not portable to BSD `find`. Only safe if the project's Windows target is confirmed to always be GNU coreutils (Git Bash ships GNU userland) — acceptable **only** if this hook is confirmed never to run under a BSD/macOS shell context. Given the project already runs on macOS in some developer environments (per existing `stat -f %m` awareness elsewhere in the codebase), do not rely on this without a platform check.
   - **Recommended fallback:** a short platform probe identical in spirit to the existing `extract_cmd` pattern already used in these hooks (try GNU form, fall back to BSD form):
     ```sh
     mtime_of() {
         local f="$1"
         stat -c %Y "$f" 2>/dev/null || stat -f %m "$f" 2>/dev/null
     }
     ```
     This mirrors the project's existing convention (seen in `extract_cmd` in both `check-commit.sh` and `post-commit-cleanup.sh`) of probing multiple implementations and falling through, rather than detecting the OS directly — consistent with the codebase's established portability idiom.
3. Regardless of source, always feed both timestamps through the same shell-arithmetic integer comparison (`[ "$sentinel_ts" -lt "$head_ts" ]`) — never a string comparison, and never a comparison that depends on locale-specific date formatting.

## Alternatives considered

| Option | Why rejected |
|--------|-------------|
| Fix `post-commit-cleanup.sh` to also match terminal commits somehow (e.g. a periodic background check) | Structurally impossible — `post-commit-cleanup.sh` only runs as a Claude Code `PostToolUse` hook reacting to a tool call; a terminal commit made outside Claude Code never invokes any Claude Code hook, so there is no event to react to. Cleanup-on-check is the only place that can observe the gap, because it runs on the *next* gated attempt regardless of what happened before it. |
| Evict only in `post-commit-cleanup.sh`, skip `check-commit.sh` | Does not close the finding — this is the status quo (cleanup only fires on matched-tool commits) and cannot detect a terminal commit that already happened. |
| Rely solely on ADR-008 content-binding, skip timestamp staleness | Content-binding answers a different question (does the reviewed tree match?) and has its own failure modes (see §Design interaction) — a tree that happens to hash-match an older approved state (rare but possible under rebase/cherry-pick) would not be caught by content-binding alone. Timestamp staleness is a cheap, orthogonal check worth keeping even if ADR-008 ships. |
| Always fail-closed including the same-second tie case | Would make the gate flaky on fast machines/scripted flows where review-write and commit can land in the same wall-clock second, for no real security benefit (worst case is one second of staleness). Tie-breaks toward "not stale" instead. |

## Consequences

- **Easier:** the terminal-commit staleness gap (finding 9) is closed without requiring any change to how developers commit — the fix is entirely inside the existing gate hook.
- **Harder / constrained:** `check-commit.sh` gains a small amount of additional logic (timestamp parse + comparison) and a platform-portability concern (mtime fallback) that did not exist before; every future change to the sentinel format (e.g. ADR-008) must keep the content-timestamp field parseable by this rule.
- **Follow-up:** implement the `check-commit.sh` eviction block, its test coverage (`tests/test-check-commit.sh`), the `/g-doctor` reuse of the same comparison, and the `workflow-checkpoint.sh` display refinement — all flagged above as follow-up (not in this wave's file scope of `post-commit-cleanup.sh` + its test file).
- **Unaffected:** the existing unconditional-delete behavior in `post-commit-cleanup.sh` for matched-tool commits; the existing sentinel-presence gate logic in `check-commit.sh` for the common case where no staleness exists.
